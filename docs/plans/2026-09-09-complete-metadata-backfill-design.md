# 全量详细信息回填与扩量设计

## 目标与验收口径

正式库中的每一条记录都必须能回答两个问题：来源实际提供了哪些详细信息，以及哪些信息来源没有公开。验收不能只看 `metadata_json` 是否非空，而要分别统计描述、作者、网页、封面、来源特有字段、transcript 状态以及可下载辅助资产。旧记录先逐来源回填，再允许扩量；新记录继续由 spider 在入库时携带同一版本化 envelope。

“全部详细信息”指公开、无需登录且能与稳定 source ID 对应的信息，不包括绕过付费墙、验证码或权限获取的内容，也不把自动 ASR 冒充成平台文本。来源确实不提供 transcript 时保存 `not_provided`；只给不可下载引用时保存 `reference_only`。

## 方案比较

1. 仅重新运行搜索 spider：实现简单，但搜索排序会变化，无法保证历史 B站分P、喜马拉雅 track 和旧小宇宙单集再次出现。
2. 按数据库 source ID 逐源定向回填（采用）：RSS/LibriVox 做全集合匹配，B站按 BV号+分P、喜马拉雅按 trackId、小宇宙按媒体 URL 中的 podcast ID 定向获取。可审计、可续跑，且不会生成重复音频记录。
3. 保存每个网页的完整快照：信息看似最多，但包含大量无关脚本、签名和易变页面状态，安全和长期可用性都差。

## 组件与数据流

新增 `metadata_backfill.py` 作为只负责元数据的 CLI。它读取现有记录并按来源分组，调用现有适配器的公开详情能力，最终统一交给 `Storage.enrich_records()`。工具支持 `--source`、`--limit`、`--workers`、`--audit-only` 和 JSON 报告路径；每个来源失败互不阻断。

回填顺序为：只读审计 → 来源定向抓取 → 按 URL 或 `(source, source_id)` 更新 → 再审计。无法解析的旧记录保持原字段，并在运行报告里列为 unresolved，不创建伪造 envelope。背景文件另由 `main.py background` 对 done 记录生成，避免元数据抓取与大文件下载耦合。

扩量采用分批门禁：先定向回填全部历史记录；然后每个来源按批次采集，批次完成后检查新增数、详细字段覆盖和错误率；合格才继续下一批。正式下载仍由 SQLite claim/lease 消费，默认同时保存背景资料。

## 错误处理与安全

定向回填继承现有公网 DNS、重定向、响应大小和 HTML 净化边界。报告只保存脱敏 URL、计数和有界错误摘要。来源下架、网络阻断或没有公开字段属于 unresolved/not_provided，不会用空值覆盖已有信息。

旧批量下载活跃期间不得启动回填或迁移。进程退出后先用 SQLite backup API 创建备份，再执行加法迁移和定向回填。

## 测试

单元测试覆盖审计分级、按稳定 source ID 匹配、空字段不覆盖、单来源失败隔离和 JSON 报告。集成验证覆盖历史正式库迁移、五个真实来源的有界定向回填、背景文件生成、sidecar JSON 全量解析、签名参数扫描和所有物理音频 ffprobe。
